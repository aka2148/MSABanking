**Audit date:** 25 October 2026. **Code baseline:** `main` at `160fecd54d98eba216dcb42b4ae5d8114d9c936e`. **Scope:** active Angular/Nginx/three-Spring-Boot/MySQL/Kafka application, with `BACKEND/` consulted only for shared Flyway SQL and legacy comparison. ## 1. What is broken, and what is only unverified?

The most concrete defect is FD premature settlement accounting: in the active MySQL FD database, **both prematurely closed FDs have a nonzero FD liability residual** although all 11 examined journal headers match their line totals. Source shows settlement debits FD liability for principal plus paid interest without first recording that interest as an FD liability/expense entry. Actual customer payout correctness was not reconstructed, so treat an incorrect payout as a **potential critical risk — verification required**, not an observed loss. The active application also has **no CASA-to-CASA transfer controller or UI**; a transfer service in retained `BACKEND/` is not compiled into the active service. Staff teller, demo opening and loan disbursement change the savings balance and savings history without journal postings. The demo clock calls transactional batch methods through `this`, bypassing the Spring transaction proxy and allowing partial writes after failure. These source-confirmed gaps are P1 for the user-requested financial demo.

The current flow can book and fund an FD in source; funding writes a savings debit, FD transaction, and two-line journal in one `@Transactional` controller method, but no isolated execution established amount, status, rollback, role, or replay correctness. Maturity is intentionally two-step in source: batch accrues/marks `MATURED`; a separate close pays linked savings and marks `CLOSED`. A maturity batch response alone means **no payout**. Whether automatic payout is required is a lab interpretation to resolve; the manual does require scheduled maturity handling and notices. Current forex is explicitly an **indicative request** with no actual conversion or live rate; the UI and API correctly disclose that limitation. Currency precision is nevertheless inconsistent: JPY is configured at 0 decimals, but Angular forms/displays and calculator assume 2, and the calculator uses `double`/`Math.pow` instead of the booked compounding rules. Customer KYC is a self-attested academic simulation. Loan application/review/disbursement exist, but there is no loan receivable/repayment lifecycle and disbursement bypasses the journal. Treat those enhancements according to agreed demo scope, not as automatic manual failures.

Authentication/onboarding has a likely HEAD startup journey blocker: OTP signup needs an email provider key, and the local `.env` boolean check found it **not configured**; current running customer image/schema can be older than HEAD. Source also inserts a primary email with `cem_is_verified` false after OTP, lacks database email uniqueness, and product/FD services keep accepting an otherwise valid signed JWT until expiry after identity-side status/role/token-version changes. None of these cross-service cases was exercised here. Six unauthenticated gateway GETs returned 403; that proves only those no-token denials. Browser workflows could not be rendered, so no claim is made that a visible button fails, a form submits, or mobile layout breaks in the running UI. Angular TypeScript/templates passed no-emit checks. Gateway `/gateway/health` returned 200 but is a static Nginx response, not a downstream readiness probe.

**Severity standard:** P0 = demonstrated money loss/creation, unauthorized financial action, major corruption, or demo-blocking core workflow; P1 = source-confirmed core gap/serious integrity or access issue; P2 = important incomplete behavior without demonstrated critical impact; P3 = usability/scale/documentation polish. **No P0 is confirmed by this audit.** The live premature liability residual is confirmed P1. Potential payout, clock-failure, cross-service revocation and stale-KYC impacts need isolated reproduction before any P0 escalation. Lab-required and optional/demo-scope items are labelled in the register.

## 3. Root-cause analysis of the main workflows

### A. CASA transfer — D02/D03

**Expected:** authenticated owner moves a positive amount between eligible same-currency savings accounts; source debit equals destination credit, both savings histories share one business reference, one balanced journal exists, and any failure rolls back. **Observed:** no active controller method, form, or posted transfer can be found. The legacy `BACKEND/src/main/java/com/bank/fd/application/SavingsTransferService.java` has ordered locks and idempotency but `services/fd-account-service/pom.xml:24-27` does not compile that Java module; `SavingsAccountController.java:27-115` has no transfer handler and the savings screen has no transfer control. Hence no active path was available to test. It is inaccurate to claim a debit was observed without credit. **Reproduce safely:** in a fresh isolated stack inspect gateway/Swagger/routes, submit a synthetic transfer to the proposed route (currently expect absent-route/handler), and verify no DB delta; after implementation use A=100.00/B=25.00, transfer 10.00, inject a failure after debit, and retry the same key. **Repair:** port focused logic into the active FD/account service with `POST /api/v1/savings-accounts/transfers`, stable-order `SELECT ... FOR UPDATE`, amount/currency/ownership/status checks, one DB transaction, idempotency unique key, two savings history entries and two journal lines. The same MySQL FD schema owns both savings accounts, so a distributed saga is unnecessary. Add Angular form and gateway contract only after service invariants pass. Migration may be needed for unique transfer reference/idempotency; inspect existing constraints before adding. **Acceptance:** A=90.00/B=35.00, two correctly signed histories, one journal, all retry/failure/concurrency cases leave conserved funds.

### B. Premature FD withdrawal — D01/D05 and D03

**Expected:** eligible owner requests quote; staff approves once; payout uses booking-governed penalty/rate, credits linked savings exactly once, closes FD, records paid interest/penalty and clears FD liability. **Observed:** source quote computes net principal+penalized interest, approval calls settlement, and settlement credits savings and debits FD liability for net. No preceding paid-interest journal exists. Read-only live aggregate found nonzero FD liability on both prematurely closed accounts. The present test `FdAccountMigrationTest.java:195-210` checks status/penalty history, not liability clearance or actual savings amount. Quote reads mutable `fd_product_currency_ref` penalty, rather than a full booking snapshot. Replay response reads maturity estimate (`fa_maturity_amount`) rather than actual net settlement. **Reproduce safely:** book/fund a synthetic FD with principal 1,000.00 and payable premature interest 5.00; close after quote, then inspect savings balance/history, `fd_transactions`, `fd_journal_lines`, `fd_accounts`, idempotency and repeated response. Do not run against existing accounts. **Repair:** freeze premature terms at booking with a carefully audited migration/default for existing FDs; decide whether penalty reduces unearned interest or is a separate charge; post Dr interest expense/Cr FD liability for *paid* interest before Dr FD liability/Cr savings for payout, in the same transaction. Persist actual payout/reference and use it for replay. No correction of existing live balances should be applied until their full ledger/customer history is reconstructed and a reversal/adjustment policy approved. **Acceptance:** settled savings credit equals calculated net, one payout, zero FD liability, consistent transaction history, no change on retry; failure before commit leaves FD open and savings unchanged.

### C. FD funding, interest, maturity and batch — D04/D09/D10/D11

**Expected:** booking validates current customer/offer/owned savings/amount/term/currency and records PENDING; funding atomically debits savings, credits FD liability, records histories and becomes ACTIVE; interest follows booked `BigDecimal` terms and configured currency scale; eligible ACTIVE FDs mature on the business date once; policy-defined payout credits savings once and closes. **Observed:** `FixedDepositController.java:40-87` contains the funding transaction and journal. `FdBatchService.java:37-60` records maturity interest and status, **without savings payout**; `FdLifecycleController.java:36-44,116-133` separately settles. `DemoClockService.advance` commits the new date before `runDaily`, and `runDaily` self-calls annotated methods, so the clock route lacks their intended transactional boundary. No FD business `@Scheduled` job was found; Kafka outbox publishers are scheduled, so saying “no scheduler” would be false. **Reproduce safely:** start with savings 1,000.00; book/fund principal 100.00, verify savings 900.00 and FD liability 100.00; move isolated business date, accrue/mature, inspect interest and MATURED with no payout; invoke close and check 100.00+interest credited; rerun every step and inject failure after status update/accrual. **Repair:** place batch writes behind a proxied transactional service per-account boundary, record durable retry progress, document whether `MATURED` is waiting for customer close or automatically settled, schedule required jobs, generate notices/statements, and align calculator with booked terms. Migrations only for durable state/notice uniqueness if existing schema lacks it. **Acceptance:** no partial maturity/journal after failure, no duplicate interest/payout on retry, status matches savings movement and report, all currency scales correct. A batch result must never be presented as proof of payout if settlement remains separate.

### D. Forex and multi-currency — D11/D15

**Expected for current contract:** a clearly labelled indicative request may persist an offered currency pair/request without moving money. **Expected only if actual conversion is in the agreed demo:** source/destination currency, directed rate, source/timestamp/expiry, fees, rounding, account ownership, balanced entries per currency with clearing/valuation rules, idempotent settlement and history. **Observed:** `LoanForexController.java:145-183` stores an indicative request; offer and UI disclose no live trade/funds transfer. There is no conversion failure to localize to gateway because no conversion exists. `forex_requests` schema lacks settlement amounts. **Reproduce safely:** with synthetic auth, submit request and confirm request row/no account delta; no claim of converted balance. **Smallest safe solution:** keep forex as disclosed request for the one-week lab demo, unless explicit evaluation requires conversion. If required, implement a separate execution contract after D03/D11, not a UI-only amount change; rate and two-currency journals require explicit policy. JPY 0/INR 2/KWD 3 scales must be tested; never compare different-currency totals directly without valuation. **Acceptance:** request-only mode claims no exchange; conversion mode proves both account balances, per-currency entries and replay.

The running image may not be HEAD, so end-to-end runtime effect remains unverified. **Reproduce safely:** in isolated data send/verify/register/login; inspect email flag; set KYC PENDING/REJECTED after application or pause Kafka then attempt financial operations; disable user/remove admin role/reset password and retry old token through each service. **Repair:** test-only OTP delivery or configured provider, normalized unique email + verified flag, explicit simulated KYC status and audited transitions, bounded snapshot freshness/current-state check for decisions, and a cross-service revocation rule. Actual RBI-style customer due diligence is outside the lab unless separately agreed; the [RBI KYC Direction](https://www.rbi.org.in/commonman/Upload/English/Notification/PDFs/MD18KYCF6E92C82E1E1419D87323E3869BC9F13.pdf) is a realism reference. **Acceptance:** registration is reproducible without exposing codes/secrets, no duplicate email, no revoked/changed-role privileged action, and no loan disbursement after KYC downgrade.

### F. Loans — D03/D08/D14/D20

**Expected for existing narrow scope:** customer submits a loan application against a configured offer and owned savings destination, staff reviews/approves or rejects, and a simulated disbursement is accurate and explicit. A full lending claim additionally requires applicant employment/income/obligations, receivable, schedule, repayments and reconciliation. **Observed:** `loan-page.html:27-39` captures currency, amount, tenure, purpose and savings destination; `LoanForexController.java` persists application/decision/disbursement and directly credits savings on disbursement, without journal or loan receivable. Cosmetic changes wait behind financial integrity.

## 4. Financial invariants and accounting mapping

The current FD schema has `fd_journals` and `fd_journal_lines` plus separate `savings_transactions` and `fd_transactions`. The journal schema constrains each header's debit total equals credit total and individual line sign, but it does not enforce every balance change has a journal or account-level clearance. The read-only active DB check found 11 journals, **0** malformed header/line aggregate totals, 5 funding, 2 interest, 4 settlement, and 2 premature FD liability residuals. These counts do not establish no duplicate business events, no orphan history, or all customer balances matching journal-implied balances. A complete bank-wide ledger is **not** currently demonstrated. Accounting mappings below are a **recommended conceptual model**, using explicit currency and business reference; `fd_journal_lines.jl_account_code` is currently free text. Corrections should use auditable offset/reversal entries, not delete history.

| Operation | Conceptual debit / credit, same currency | Current posting and invariant |
|---|---|---|
| Simulated savings opening/teller deposit | Dr simulated cash/clearing, Cr savings liability | Balance/history only; journal gap. |
| Teller withdrawal | Dr savings liability, Cr simulated cash/clearing | Balance/history only; journal gap. |
| CASA transfer | Dr source savings liability, Cr destination savings liability | Active operation absent. Both histories, balances, journal and idempotency must commit together. |
| FD funding | Dr savings liability, Cr FD liability | Source code posts two lines. Savings debit must equal FD principal; failure leaves PENDING and original balance. |
| FD interest payable | Dr interest expense, Cr FD liability | At maturity source code posts this; daily memo accrual rows are not necessarily financial postings. Rerun once only. |
| Periodic FD interest payout, if offered | Dr interest expense or accrued-interest liability, Cr savings liability | No separate active periodic customer payout path found; do not present capitalization as cash paid. |
| Normal FD settlement | Dr FD liability, Cr savings liability | Source code posts this; closed FD liability should be zero. |
| Premature FD interest and settlement | Dr interest expense, Cr FD liability for paid interest; then Dr FD liability, Cr savings liability for net payout | First leg missing. If penalty is rate reduction, expense is already net; if separate fee, define explicit receivable/income leg. |
| Product fees or separate premature charge, if actually levied | Dr savings liability or FD liability, Cr fee income/clearing under a disclosed policy | Charges exist in product configuration, but no general fee-posting path was established; a penalty history row alone is not a balanced fee journal. |
| Loan disbursement if real lending | Dr loan receivable, Cr savings liability | Savings credit/history only today; receivable and repayment absent. |
| Loan repayment, if servicing is added | Dr savings liability, Cr loan receivable and earned interest income according to terms | No active repayment lifecycle found; not a current posting. |
| Indicative forex request | No financial entry | Correct for request only. Real execution would need separate directed rate, clearing and per-currency entries. |
| Actual forex conversion, only if later implemented | Dr/Cr source-currency savings/clearing and destination-currency clearing/savings in separate currency-balanced sets with documented valuation and fees | No execution path or live rate exists; not a current posting. |
| Reversal/correction, only if later supported | New offsetting entry referencing the original, with corresponding customer balance/history correction | No active reversal workflow found; deleting/updating old journal rows would destroy the audit trail. |

For **every** completed journal, `SUM(debits)=SUM(credits)=header amount`, with at least one positive line each side, within its currency and scale. Every posted business reference must be unique across retries; any customer balance change needs one corresponding journal and history; a closed FD should have zero principal/interest liability after settlement. Do not sum INR and JPY as though they were one value. There is no evidence that two separate ledger implementations post the same event; existing histories and journals have distinct roles. Cross-service changes need a durable reference/event and reconciliation if they ever span owners, but current savings and FD balances share the FD MySQL database, so focused local transactions are sufficient for core flows. Kafka snapshots/outbox should carry eligibility/reference updates, not silently post a second monetary movement. [Basel Core Principle 26](https://www.bis.org/committees/bcbs/basel-framework/standard/bcp?allChapters=true) supports reconciliation and independent controls as a banking practice reference; the lab can implement a small, explainable subset.

## 5. Architecture, KYC and loan implementation boundaries

**Service ownership.** Identity owns credentials, customer and KYC; Product owns offers/currency definitions; FD/account owns savings, FD, applications, journals. Keep balance changes and their journal entries inside the FD database transaction. Use product/customer snapshots for read models, with explicit freshness or authoritative check at financial decision points. Do not add a saga, workflow engine, real payment rail or real FX feed for the college demo unless an actual cross-database financial action is introduced. For such a future action, durable business references, outbox delivery, idempotent consumers and reconciliation would be necessary.

**Minimum KYC demo plan.** Keep customer identity/contact/address plus status, risk category, submitted/decision timestamps, reviewer/reason and immutable audit events. Use existing KYC/customer tables and add only fields/constraints missing after schema inspection. Customer endpoints should support draft, submit, document metadata/upload and status; staff endpoints should review/approve/reject with allowed transitions; never expose full documents/PII in logs. The current automatic nine-field `AUTO_VERIFIED` behavior must be explicitly labelled as simulation or replaced with staff approval if the demo promises review. The frontend `/kyc` should show required next action and current status; staff `/staff/customers` should display decision fields and reason. Enforce eligibility in FD/loan (and any future transfer/forex execution) on the backend using current-enough state; define whether existing accounts remain operable after later KYC downgrade. Normalize duplicate identity/email handling and use synthetic fixtures. Test INCOMPLETE→PENDING→VERIFIED/REJECTED, invalid transitions, owner/staff permissions, stale snapshot, and audit trail. Genuine verification-provider integration is future scope, not a lab prerequisite.

**Minimum loan plan.** Current application already has amount/currency/term/purpose/destination and status history. If the demo claims only “apply/review/simulated disbursement,” preserve that narrow contract while fixing eligibility and accounting. If it claims underwriting/repayment, add occupation/employer/income/obligations from Angular form → request DTO validation → application columns/events → review response, then define approved principal/rate/term, receivable and a simple schedule/repayment path. Migrate existing applications with nullable/backfill policy; do not mark existing records as verified income. Test every field round trip and state transition, duplicate submit/approve/disburse, KYC downgrade, and journal/receivable equality. Product offer rules/charges must either be evaluated or visibly disclosed as ineligible, not silently omitted.

**Migration and release provenance.** Run clean-schema and upgrade-path Flyway checks only on fresh isolated volumes; account for active services pointing to host MySQL schemas rather than healthy Compose DBs. The active FD DB reports Flyway V11; the running customer image reports V6 while HEAD includes customer V7. Do not restart the existing customer service merely to align versions: startup Flyway may alter preserved records. Migrations should be additive, auditable, with existing-row decisions documented and rollback/recovery through backups, not destructive cleanup.
