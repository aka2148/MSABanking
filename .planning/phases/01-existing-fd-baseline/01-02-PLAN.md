<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Legacy PostgreSQL data → V6 migration | Existing rows can violate the new invariants or contain duplicate UUIDs. |
| Application mutation → FD account row | Concurrent lifecycle operations can race without row version/locking. |
| Client retry identity → operation table | A caller-controlled key must be scoped and cannot be trusted as a global unique identifier. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-04 | Tampering | `V6__fd_lifecycle_baseline.sql` | mitigate | Run explicit legacy preflight queries, add named PostgreSQL checks, and fail the migration with a diagnostic instead of deleting or coercing rows. |
| T-01-05 | Denial of service | migration validation | mitigate | Validate before adding constraints and report the offending invariant so deployment does not fail with an opaque catalog error. |
| T-01-06 | Tampering | operation idempotency | mitigate | Scope the unique key by operation and actor, store a request hash, and enforce uniqueness in PostgreSQL rather than using JVM memory. |
| T-01-07 | Elevation of privilege | account repository | mitigate | Provide locked persistence access for service-layer authorization/transition checks; no controller-facing direct repository access is added. |
</threat_model>
